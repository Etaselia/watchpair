# Manual alpha rollout — 2026-10-29

The existing VPS now serves WatchPair **2.0.0-alpha.2** at [the download and setup page](https://38-180-216-137.sslip.io:8443/downloads/). This is an operator-authorized alpha trial using the existing validation signing key. Watching requires the desktop app and new v2 rooms; v1 rooms/history were intentionally not migrated.

## Deployed services and artifacts

- Coordinator: `watchpair-v2-coordinator`, private port 8787, persistent SQLite under `/opt/watchpair-v2/data`.
- Relay: `watchpair-v2-relay`, private port 8788, separate process forwarding opaque authenticated frames in memory. Public routing uses the same HTTPS origin and `/v2/relay/*`.
- Edge: `watchpair-proxy`, existing Caddy image/certificate volumes, public ports 80 and 8443. Plain HTTP explicitly redirects to HTTPS **port 8443**. Only `NET_BIND_SERVICE` is added back after dropping capabilities; the image's executable requires it to start.
- Both Node services use the tested image `sha256:8704814a5e6038f4d39cc15487ffdb37e5042620b170564b67aafd7d7b73c5c8`, tagged `watchpair-v2:2.0.0-alpha.2`.

## Live verification

- Certificate-verified public HTTPS and authenticated WSS: two members, queue editing, manual watched history/timestamps and separate relay transport passed. [Report](../../outputs/v2-public-smoke.log).
- An online SQLite backup verified successfully. Existing host and guest credentials, queue and watched timestamps survived a real coordinator restart. [Report](../../outputs/v2-public-restart.log).
- Eight authenticated public WebSocket members received the authoritative state. [Report](../../outputs/v2-public-eight-members.log).
- The exact packaged Windows and Linux applications connected over public HTTPS/WSS in isolated profiles and received their room snapshot, queue and history. Linux ran under Ubuntu 24.04/WSL/X11; this is not physical Linux hardware qualification.
- The signed public feed was checked against the pinned Ed25519 key. The native updater on each platform fetched its actual VPS archive, verified the signature/hash, extracted it and staged the newer version. [Windows report](../../outputs/v2-public-signed-update-windows.txt), [Linux report](../../outputs/v2-public-signed-update-linux.txt).
- The Linux public update check took approximately 46 seconds; Windows took approximately 166 seconds. Two earlier Windows checks exceeded the fixture's 90-second download/staging wait, including an isolated run. Their [concurrent](../../outputs/v2-public-signed-update-windows-concurrent-timeout.txt) and [isolated](../../outputs/v2-public-signed-update-windows-isolated-timeout.txt) failure reports are retained. The final Windows check used the explicit `WATCHPAIR_UPDATE_TEST_TIMEOUT_MS=240000` operator setting; all integrity and staging assertions remained unchanged. This test-only option is bounded to 90–600 seconds and leaves the default loopback budget at 90 seconds. No application binary or public archive changed to obtain this pass.
- The final download page was visually inspected in a real browser. Archive responses advertise the exact size and byte-range support. HTTP redirects to the working HTTPS port.
- After the live checks, all three WatchPair containers ran without OOM events or unexpected restarts. Approximate working sets were 53 MiB coordinator, 28 MiB relay and 21 MiB proxy. Resource limits, bounded logs and relay buffers are in the rollout guide.

## Removal and operational limits

The stopped v1 application container, `watchpair:0.14.0`, `watchpair:rollback` and obsolete `/opt/watchpair` configuration were removed. Small configuration backups were saved privately on the operator machine. No media or unrelated VPS service was removed. Removing the old application reclaimed approximately **290 MB**; the VPS had approximately **795 MB free** afterwards, versus 506 MB immediately before cleanup.

The legacy **Deploy VPS** GitHub workflow is disabled. Its root-side deployment helper was retained unchanged; replacing it was declined by automatic approval review. Scheduled v1 deployment cannot run through the disabled workflow. Re-enabling legacy deployment requires a separate operator decision.

The disposable rollout test room and its eight test members were removed through the room API. A verified post-cleanup SQLite backup, relay environment and deployment receipt were saved privately on the operator machine. The private signing key stayed local throughout the rollout.

The server has a 5 GB disk and 712 MiB RAM. Relay limits are 2 MiB/s globally in each direction, 1 MiB/s per channel, a 16 MiB buffer budget and 128 channels. Monitor space before retaining additional desktop versions. Native hardware decoding, physical Windows 11/Linux GPU and audio coverage, and the other hardware limits in `IMPLEMENTATION.md` remain release-candidate work. This rollout verifies operator deployment and native connectivity; it does not assert full WAN playback/drift qualification on physical devices.
